# CivilStock 설계 제안 (초안)

> 유저가 직접 국가를 세우고, 경제·전쟁·외교를 자유롭게 벌이는 오픈 웹앱 게임.
> Google(Firebase) 환경. 2DStock의 아쉬웠던 점을 정면으로 개선한다.

## 0. 2DStock 회고 — 무엇이 아쉬웠나

2DStock 아키텍처를 그대로 요약하면:

- **시장은 클라이언트에서 결정론으로 계산**(고정 기원점) → 모두가 같은 세계를 봄.
- **Supabase는 계정 레이어**(로그인·지갑 저장·랭킹)만 담당.
- 정적 사이트(GitHub Pages) 배포.

여기서 나온 구조적 한계:

1. **유저 간 실질 상호작용이 없다.** 전쟁·외교가 스크립트/스케줄 이벤트지, 상대
   플레이어를 향한 행위가 아니다. 사실상 "공유된 시뮬레이션을 상대로 한 솔로
   플레이 + 랭킹".
2. **클라이언트 권위 → 조작에 취약.** README도 "e스포츠급 검증이 아니라 캐주얼
   조작 억제용"이라고 명시.
3. **기능 스프롤.** 시장·IPO·옵션·공매도·ETF·미니게임 등 100+ 파일. 재미의 축이
   분산됨.
4. **세계가 지속되지 않는다.** 회차/프레스티지 리셋 루프라 "내가 쌓은 것이 세계에
   남는다"는 감각이 약함.

CivilStock은 이 4가지를 뒤집는다: **서버 권위형·지속되는·유저가 만드는 세계.**

## 1. 핵심 방향 전환 3가지

| 축 | 2DStock | CivilStock |
|---|---|---|
| 권위 | 클라이언트 결정론 | **서버 권위**(Cloud Functions) |
| 상호작용 | 없음(솔로+랭킹) | **유저 간 국가 상호작용**이 게임의 본체 |
| 세계 | 회차마다 리셋 | **지속 세계 + 6개월 시즌 소프트 리셋** |

### 확정된 방향 (오너 결정, 2026-08-03)

- **세계 모델: 6개월 시즌제 / 소프트 리셋.** 한 시즌이 반년으로 길다 → 시즌
  *중* 반스노우볼이 특히 중요(§3.6). 개인 업적은 레거시/명예로 계승.
- **국가 단위: 1인국 + 멀티플레이어 병행.** 솔로는 1인 국가, 원하면 여러 유저가
  한 국가에 소속(역할 분담). 진입은 쉽게, 깊이는 확보.
- **스택: Google Cloud Run + GCP.** Firestore+Functions 대신 **Cloud Run에 올린
  권위 서버**가 세계를 직접 운영(§4).

## 2. 왜 "틱 기반 비동기"인가 (트위치 실시간 아님)

웹앱 게임의 최대 현실: **플레이어가 24시간 접속하지 않는다.** 실시간 RTS로 만들면
접속 안 한 사람이 일방적으로 털린다. 그래서:

- 세계는 **정기 틱**으로 전진한다. 예: 현실 1시간 = 게임 1일, 하루 24틱.
- 모든 국가는 **정책(policy)으로 자동 운영**된다 — 세율, 생산 우선순위, 국방
  태세, 교전 규칙(ROE). 접속하지 않아도 내 국가는 내 정책대로 굴러간다.
- 접속은 "정책을 바꾸고, 외교를 하고, 전쟁을 선포하는" 의사결정의 순간이지,
  "APM으로 손을 놀리는" 순간이 아니다.
- 전투/침공은 즉발이 아니라 **여러 틱에 걸쳐 진행** → 방어자가 대응(동맹 소집,
  방어 정책 전환, 강화 요청)할 시간을 보장. 오프라인이어도 자동 방어 발동 +
  푸시 알림.

이게 웹앱·모바일·비동기 플레이와 서버 비용(Cloud Scheduler 틱) 모두에 맞다.

## 3. 게임 시스템

### 3.1 국가 설립 (1인국 + 멀티 병행 — 확정)
- 공유 맵(헥스/지역 그리드). 빈 영토에 깃발을 꽂아 건국.
- 초기 자원 1인 지급, 수도 1칸. 신생국은 **보호 기간**(예: 실시간 3일 / 일정
  국력 도달 전까지) 동안 침공 불가.
- **솔로 = 1인 국가**로 온전히 플레이 가능(혼자서도 완결). **멀티 = 여러 유저가
  한 국가에 소속**해 지도자·장관(경제)·장군(군사)·외교관 역할을 나눔. 길드 = 국가.
- 설계 요구사항: 1인국이 멀티국에 일방적으로 밀리지 않도록 **국력은 소속 인원수가
  아니라 영토·경제 산출**로 결정. 멀티는 "관리 대역폭"(동시 정책 운용·24시간 커버)
  이득이지 수치 뻥튀기가 아니게 한다.

### 3.2 경제 (여기서 큰 수 모듈이 핵심)
- 자원 → 생산 체인 → 재화 → 시장. 처음엔 2~3종으로 좁게 시작(식량·자재·통화).
- **국고·GDP·통화 발행량은 천문학적 수**가 된다 → `exactAmount`(BigInt 문자열)로
  전부 처리. Firestore엔 문자열로 저장, Function에서 BigInt 연산. float 금지.
- 국가별 **자국 통화** 발행 가능 → 환율/인플레이션. 통화를 찍으면 물가가 오른다
  (하이퍼인플레 리스크 = 전략 선택).
- 유저 간·국가 간 **무역**: 자원 수출입, 관세, 금수(embargo).
- 세금·국채: 국채 발행으로 전쟁 자금 조달 → 이자 부담이라는 반대급부.

### 3.3 외교
- 조약 시스템: 불가침, 동맹, 자유무역, 통행권, 연방/합병.
- **평판(신뢰도)**: 조약 파기·기습 선전포고는 평판을 깎아 향후 동맹 성사율↓.
- 연합(coalition): 패권국에 맞서 다수가 자동/수동 결집 → 스노우볼 억제(3.6 참고).
- 스파이/첩보(후순위): 정보 비대칭이 외교의 재미.

### 3.4 전쟁
- 군대 = **경제 산출을 전환**해 만든 것(병력·장비 = 자원 소모). 즉 전쟁은
  경제를 태우는 행위 → 남발 불가, 전략적 선택.
- 선전포고 → 동원 → 다틱 교전 → 영토 점령/약탈. 전쟁 피로도(war exhaustion)로
  장기전은 국내 경제·안정도에 페널티.
- 점령해도 즉시 편입 아님: 점령지 저항/치안 유지 비용 → "정복만능" 방지.
- 방어 우위 설계: 수성이 공성보다 유리하게 기본 세팅(오프라인 방어 보호).

### 3.5 내정·정치
- 정부 형태(민주정/과두정/전제정 등) 각각 트레이드오프: 생산 보너스 vs 반란
  리스크 vs 정책 변경 속도.
- 안정도/여론: 세금·전쟁·물가가 안정도에 영향. 낮으면 반란·분리독립.
- 멀티 플레이어 국가는 내부 정치(쿠데타, 선거, 권력 분배)가 그 자체로 콘텐츠.

### 3.6 반(反)스노우볼 — 지속 세계 게임의 생사

지속 세계의 최대 적은 **강자독식·신규 절망**. 대응 장치를 처음부터 박는다:

- **규모 역페널티**: 영토·인구가 클수록 유지비·부패·관리 난도 상승(수확체감).
- **신생국 보호 + 캐치업**: 후발 주자에 성장 보너스, 약소국 연합 보너스.
- **연합 자동 형성**: 1위 패권국을 향한 외교 페널티/연합 결성 유인.
- **전쟁 피로·점령 비용**: 무한 정복 억제.
- **시즌(6개월) 소프트 리셋**: 지속 세계지만 반년 주기로 새 지도 리셋. 개인은
  **레거시/명예 포인트**(2DStock 프레스티지의 세계 스케일 버전)와 칭호·스킨·시작
  보너스를 계승. "내 업적은 남고, 판은 새로 열린다."
- **6개월은 길다 → 시즌 *중* 반스노우볼이 핵심.** 리셋만으로는 반년 내내 이어지는
  패권을 막지 못한다. 그래서 위의 규모 역페널티·연합 자동 형성·전쟁 피로를
  **시즌 내내 상시 작동**시키고, 추가로 시즌을 **단계(chapter)**로 나눈다:
  - 초반(보호·성장) → 중반(팽창·경쟁) → 종반(정산). 종반에는 **최종 목표
    점수전**(영토·경제·전쟁 업적 합산)으로 승패를 가려, 중반에 앞선 국가도
    종반까지 방심할 수 없게 한다.
  - 시즌 중 **주간 목표/이벤트**(자원 러시, 국지 분쟁존 개방)로 판을 흔들어
    한 세력의 고착을 방지.

## 4. 기술 아키텍처 (Google Cloud Run + GCP — 확정)

Firestore+Functions가 아니라 **Cloud Run에 올린 권위 서버**가 세계를 운영한다.
국가 경제·전쟁은 *트랜잭션이 무겁고 관계형*(자금 이체, 전투의 원자적 정산,
불변식 검증)이라 Firestore보다 **관계형 DB + 서버 트랜잭션**이 잘 맞는다.

```
[웹앱 클라이언트]  ──읽기(REST/구독)──▶ ┌──────────────────────────────┐
   (Next.js SPA,   ──액션(HTTPS/WS)──▶  │  Cloud Run: 권위 API 서버     │
    Cloud Run/CDN)                       │  (Node/TS, 모든 변경 검증)     │
                                         └──────────────┬───────────────┘
[Cloud Scheduler] ──정기 틱(HTTP)──▶  Cloud Run: worldTick 잡 ──▶ Cloud SQL
                                         (경제 정산·전투 판정·이자)     (Postgres)
Identity Platform / Google 로그인          Memorystore(Redis): 세션·실시간 팬아웃·락
Cloud Messaging(FCM): 피침·조약·틱 결과 푸시
```

- **모든 세계 상태 변경은 권위 서버 API를 거친다.** 클라이언트는 DB에 직접
  접근하지 않음(자격증명 미노출). → 2DStock의 클라이언트 권위 문제를 원천 차단.
- **DB 권장: Cloud SQL(Postgres).** 자금 이체·전투 결과 반영을 **DB 트랜잭션**으로
  원자화(음수 국고 금지·자원 보존 같은 불변식을 제약/트랜잭션으로 강제). 큰 수는
  `NUMERIC`으로도 담을 수 있으나, 저장/전송은 **정수 문자열**로 통일해 클라이언트·
  서버가 같은 `exactAmount`를 공유(§ 큰 수 처리).
- **worldTick**: Cloud Scheduler가 N분마다 Cloud Run 엔드포인트를 호출 → 활성
  국가들의 생산·세수·이자·전투·안정도를 배치 정산. 틱 잡은 **멱등**(중복 호출
  안전)하게, 진행 중 재시작에도 이중 정산이 없게 설계.
- **실시간성**: 클라이언트는 SSE/WebSocket(Cloud Run)로 지도·시장·전황을 구독.
  팬아웃·프리즌스·틱 락은 Memorystore(Redis). 고빈도 일시 데이터는 Redis에 두고
  영구 상태만 Postgres에 커밋.
- **큰 수 처리**: `src/lib/number/exactAmount.ts` — 클라이언트(표시)와 서버(연산)가
  **동일 모듈 공유**. JSON/일부 저장 경로가 BigInt를 못 담으므로 정수 문자열로
  다루는 이 설계가 그대로 유효. (이미 이식·테스트 완료.)
- **부정행위 방지**: 서버 권위 + 액션 rate limit + 서버 측 불변식 검증 + 틱 멱등성.

## 5. MVP 범위 (기능 스프롤 재발 방지)

2DStock의 교훈: **한 번에 다 만들지 않는다.** 수직 슬라이스부터.

**MVP (재미의 최소 루프 1개):**
1. Google 로그인 → 국가 건국(맵에 깃발) → 수도 1칸.
2. 단순 경제: 자원 1~2종 + 국고. worldTick으로 생산·세수 정산.
3. 다른 유저와 **무역 1건** 체결.
4. **불가침 조약 1건** 체결/파기(평판 변동).
5. **선전포고 → 다틱 전투 → 영토 1칸 점령**의 완결.
6. 피침 시 푸시 알림 + 오프라인 자동 방어.

이 루프가 "재밌다"가 확인되면 통화/인플레·정부형태·연합·에포크·첩보를 순차 확장.

## 7. 남은 세부 결정 (확정된 방향 안에서)

큰 방향은 §"확정된 방향"에서 정해졌다. 다음 구현 착수 전 세부만 확정하면 된다.

- **DB**: Cloud SQL(Postgres) 권장(관계형·트랜잭션·불변식). 이의 없으면 이대로.
- **프론트 프레임워크**: Next.js vs Vite SPA. (백엔드가 Cloud Run이라 프론트는
  자유. 2DStock 자산 재활용이면 Next.js.)
- **맵 모델**: 헥스 그리드 / 지역-노드 그래프 / 자유 좌표 — 전투·인접 판정 난도가
  다름. 지역-노드 그래프가 웹앱 규모에 가장 무난.
- **틱 주기**: 현실 1시간 = 게임 1일(하루 24틱) 가정 — 확정 필요.
- **6개월 시즌의 실제 서버 운영**: 시즌 종료 시 스냅샷 아카이브 + 레거시 정산
  배치 설계.

## 8. 다음 단계 제안

1. 이 문서 방향 확정 → 2. 도메인 데이터 모델(국가·영토·자원·조약·전쟁) 스키마 →
3. worldTick 정산 로직(경제만 먼저, 큰 수 모듈 위에서) →
4. Cloud Run 권위 서버 골격 + 인증 → 5. MVP 수직 슬라이스(§5).
